# Data Model: BizFlow AI Comprehensive Test Suite

**Date**: 2025-12-11  
**Feature**: Comprehensive Test Suite  
**Phase**: 1 - Design & Contracts

## Overview

This document defines the data model for the test infrastructure, including entities, relationships, and data flow patterns.

## Entities

### TestSuite

**Description**: Collection of test files organized by test type within a project

**Attributes**:

- `projectName`: string - Name of the Nx project
- `testType`: 'unit' | 'integration' | 'component' | 'e2e' - Type of tests
- `testFiles`: TestFile[] - Array of test files
- `coverage`: CoverageReport - Code coverage metrics
- `executionTime`: number - Test execution time in seconds

**Relationships**:

- Belongs to one Nx Project
- Contains multiple TestFile entities
- Has one CoverageReport

**Validation Rules**:

- `projectName` must be a valid Nx project name
- `testType` must be one of the defined types
- `testFiles` must not be empty
- `executionTime` must be non-negative

---

### SharedTestingLibrary

**Description**: Common test utilities, mocks, fixtures, and helpers used across all projects

**Attributes**:

- `mocks`: MockUtilities - LLMService and Supabase mocks
- `fixtures`: TestFixtures - Reusable test data for all modules
- `helpers`: TestHelpers - API route and component test helpers
- `assertions`: AssertionHelpers - Common assertion utilities

**Relationships**:

- Used by all TestSuite entities
- Provides utilities to all projects

**Validation Rules**:

- All utilities must be exported from `src/index.ts`
- All utilities must be type-safe (TypeScript)
- Mocks must simulate real service behavior

---

### MockLLMService

**Description**: Test double that simulates LLMService behavior without actual API calls

**Attributes**:

- `process`: jest.Mock - Mock function for LLMService.process()
- `defaultResponse`: LLMResponse - Default mock response
- `customResponses`: Map<string, LLMResponse> - Custom responses for specific scenarios

**Relationships**:

- Provided by SharedTestingLibrary
- Used by all module unit tests
- Used by all API route integration tests

**Validation Rules**:

- `process` must be a Jest mock function
- `defaultResponse` must match LLMResponse type
- `customResponses` must be keyed by scenario identifier

---

### TestFixtures

**Description**: Reusable test data (valid/invalid inputs, mock LLM responses, expected outputs)

**Attributes**:

- `ecommerce`: EcommerceFixtures - Ecommerce module test data
- `realestate`: RealEstateFixtures - Realestate module test data
- `pt`: PTFixtures - PT module test data
- `llm`: LLMFixtures - LLM service test data

**Relationships**:

- Provided by SharedTestingLibrary
- Used by all module tests
- Used by all API route tests

**Validation Rules**:

- All fixtures must use proper TypeScript types from modules
- Valid and invalid fixtures must be provided
- Fixtures must be consistent across tests

---

### TestUtilities

**Description**: Helper functions for common test operations

**Attributes**:

- `apiRouteHelpers`: APIRouteHelpers - Next.js API route test helpers
- `componentHelpers`: ComponentHelpers - React component test helpers
- `assertionHelpers`: AssertionHelpers - Common assertion utilities

**Relationships**:

- Provided by SharedTestingLibrary
- Used by all test files

**Validation Rules**:

- All helpers must be type-safe
- Helpers must reduce test boilerplate
- Helpers must be well-documented

---

### NxTestTargets

**Description**: Project-level test execution targets configured in project.json

**Attributes**:

- `projectName`: string - Name of the Nx project
- `executor`: string - Nx executor (e.g., '@nx/jest:jest')
- `options`: TestTargetOptions - Test execution options
- `outputs`: string[] - Test output paths

**Relationships**:

- Belongs to one Nx Project
- Executes one TestSuite

**Validation Rules**:

- `projectName` must be a valid Nx project name
- `executor` must be a valid Nx executor
- `options.jestConfig` must point to valid Jest config file

---

### TestCoverageReport

**Description**: Code coverage metrics generated by Jest for each project

**Attributes**:

- `projectName`: string - Name of the Nx project
- `coverage`: CoverageMetrics - Coverage percentages by metric
- `files`: FileCoverage[] - Coverage per file
- `generatedAt`: Date - Report generation timestamp

**Relationships**:

- Generated by one TestSuite
- Belongs to one Nx Project

**Validation Rules**:

- `coverage` must include statements, branches, functions, lines
- Coverage percentages must be between 0 and 100
- Target coverage is 80%+ for critical paths

## Data Flow

### Test Execution Flow

```
Developer runs: nx test <project-name>
    ↓
Nx resolves project dependencies
    ↓
Nx executes test target from project.json
    ↓
Jest loads test files from __tests__/ directory
    ↓
Tests import utilities from distributed locations:
  - LLM mocks: @bizflow/shared/llm/src/__tests__/utils
  - Module fixtures: modules/*/src/__tests__/utils/fixtures
  - Web helpers: apps/web/src/__tests__/utils
    ↓
Tests execute with mocked services
    ↓
Jest generates coverage report
    ↓
Nx caches test results
    ↓
Test results displayed to developer
```

### Mock Data Flow

```
Test imports fixture: import { createEcommerceInput } from '../utils/fixtures'
    ↓
Fixture factory provides typed test data
    ↓
Test uses fixture in test case: const input = createEcommerceInput()
    ↓
Test verifies behavior with fixture data
```

### Mock Service Flow

```
Test imports mock: import { createMockLLMService } from '@bizflow/shared/llm/src/__tests__/utils'
    ↓
Test creates mock instance: const mockLLMService = createMockLLMService()
    ↓
Test configures mock response: mockLLMService.process.mockResolvedValue({ ... })
    ↓
Test injects mock into service under test
    ↓
Test executes and verifies behavior
```

## Type Definitions

### TestFile

```typescript
interface TestFile {
  path: string;
  testType: 'unit' | 'integration' | 'component' | 'e2e';
  testCases: TestCase[];
  executionTime: number;
}
```

### CoverageMetrics

```typescript
interface CoverageMetrics {
  statements: number; // Percentage
  branches: number; // Percentage
  functions: number; // Percentage
  lines: number; // Percentage
}
```

### TestTargetOptions

```typescript
interface TestTargetOptions {
  jestConfig: string;
  passWithNoTests?: boolean;
  coverage?: boolean;
  watch?: boolean;
}
```

## Validation Rules

### Test Suite Validation

- All test files must be in `__tests__/` directory
- Test files must follow naming convention (`*.test.ts`, `*.spec.ts`)
- Test files must be co-located with source code
- Test files must be independent (no test dependencies)

### Mock Validation

- Mocks must simulate real service behavior
- Mocks must be type-safe
- Mocks must support multiple scenarios
- Mocks must be reset between tests

### Fixture Validation

- Fixtures must use proper TypeScript types
- Fixtures must be consistent across tests
- Fixtures must include both valid and invalid data
- Fixtures must be well-documented

---

## Summary

The test infrastructure data model defines entities for test suites, shared testing library, mocks, fixtures, utilities, and test targets. All entities follow TypeScript type safety and Nx monorepo conventions. The data flow patterns ensure efficient test execution and consistent test patterns across all projects.
